## The one thing this milestone must not get wrong

**Every other subsystem in this project fails by producing nothing. This one
fails by producing something.**

M7's rule was that a wrong row renders identically to a right one. That is
still true, and M8 makes it worse in a specific way: the other nine providers
are *predicates over a repository*. Their failure mode is a wrong `ORDER BY`
or a missing filter — bounded, deterministic, and reproducible from the same
database twice. A curated row is generated by a system whose entire competence
is producing fluent, confident, plausible output, and which has no access to
the truth conditions of anything it says.

So the failure modes are new in kind:

1. **A row about titles that do not exist.** The model is handed a pool and
   asked to choose from it. Nothing in the model's architecture obliges it to.
2. **A row about titles that exist and are not in the pool** — worse, because
   they are real, resolvable, and wrong: the household is shown a shelf of
   films it does not own and cannot play, under a heading that implies it can.
3. **A row that is fluent and empty.** "Slow-burn sci-fi for a rainy night"
   over five titles the model picked because they were adjacent in the prompt.
   There is no assertion that separates this from a good row, and there never
   will be.
4. **Total silent loss.** The generation ran, cost money, wrote an
   `llm_calls` row saying `ok = true`, and produced zero curated rows — and
   the home screen looks exactly as it does when the household simply has no
   curated rows yet. **This one is measured below and it is the one that
   actually happened**, on the first shape anybody would write.

Against those, three rules for this milestone:

1. **The validator is the security boundary, and it does not trust the
   schema.** A provider enforcing a JSON schema guarantees *shape*. It says
   nothing about whether an identifier denotes anything. Every id crossing
   from the model's output into `curated_rows` is checked against the pool
   that was sent, by value, after coercion — and **the two reasons an id can
   be dropped are counted separately**, because "the model invented it" and
   "my comparison was wrong" produce the identical empty screen.
2. **A curated row is additive, and the screen must be correct without it.**
   [PRD 08](../prd/08-operations.md)'s degradation table already says so:
   *"LLM call fails → Previous curated rows persist. Home composes without
   them."* Nothing about `GET /home` may become contingent on curation having
   run, which is also what keeps M9's RFC 9457 envelope deferred (below).
3. **Every number this milestone reports about the model must carry its
   sample.** One model, one pool, one evening is not a rate. The measurements
   below say which model and how many calls, and the plan quotes them that way
   or not at all.

The second-order version: **`curated_rows` is the first table in this project
whose contents no re-run reproduces.** `title_neighbors` can be diffed against
a fresh computation; `search_document` has
`test_the_stored_document_equals_a_freshly_computed_one`. A curated row has no
oracle and is not even deterministic. The discipline has to live in the
validator and in the pool, because it cannot live in a comparison.

## Scope

M8 delivers the curation family whole — the `LLMClient` implementation, the
candidate pool, `CurationService`'s assemble→call→validate→persist,
`curated_rows`, `llm_calls`, `LLMRow`, `CuratedProvider`,
`RowFamily.CURATED`, `JobKind.CURATE`, `POST /admin/rows/regenerate` and
`usher curate` — plus the two items PRD 09 assigns it by name: M6's query
expansion, and the MovieLens tag vocabulary.

### The boundary calls

Eight, each with its reason, each recorded in PRD 09 in the same commit as the
change it describes.

**1. `LiteLLMClient` is not built. The client is an OpenAI-compatible HTTP
client over the httpx stack this project already has.** Three PRD sections
name litellm ([01](../prd/01-architecture.md)'s ports and stack tables,
[06](../prd/06-rows-and-recommendations.md)'s step 2,
[10](../prd/10-telemetry-and-dashboards.md)'s *"litellm reports per-call cost
natively"*), and all three are corrected rather than implemented. The cost was
measured rather than argued — see *Ground truth* below — and it is **+146 MB
and 29 distributions against +0 and 0**, on a project whose whole image is
356 MB and which has already refused one dependency of this shape
([ADR-0022](../prd/decisions/0022-the-embedder-is-optional-and-its-contract-is-measured.md)).
The deciding fact is not the size, though: it is that **`base_url` already is
the provider abstraction.** OpenAI, OpenRouter, Together, Groq, DeepSeek,
Mistral, vLLM, llama.cpp, Ollama and LM Studio all serve
`POST /v1/chat/completions`; what litellm adds over that is Anthropic's and
Gemini's *native* wire formats, both of which are reachable through
OpenRouter. [ADR-0027](../prd/decisions/0027-the-llm-client-is-one-http-call.md).

**2. Generation is a job. It is never on a request path, and
`POST /admin/rows/regenerate` enqueues and returns.** PRD 06 already says
*"Generation happens in a background job — never in the request path"* and
`LLMRow.build()` *"only hydrates stored output"*. The route is bundled with
this family by M7's boundary call 2 while every other admin route is M9's, so
it ships — as a **202 with the enqueued job's key**, not as a synchronous
generate. That is not squeamishness about latency: a synchronous route is the
first request in this project whose honest answer is *"the upstream is down"*,
and it would force [PRD 07](../prd/07-client-api.md)'s RFC 9457 envelope a
milestone early, against a deferral that has now survived two client-facing
routes on structural grounds rather than on inertia. Enqueued, the only
failure left is "the queue is unreachable", which is Postgres, which is
already a total outage.

**3. The prompt addresses candidates by a small integer index, and the service
owns the index→UUID map.** Measured three ways over one real 200-film pool:
a UUID handle costs **3.1× the prompt tokens and 3.2× the latency** of an
integer index **and is the least accurate of the three**. This is not a
micro-optimisation, it is the difference between a pool that fits a small
model's context and one that does not — and the map is what makes an
out-of-pool id *unrepresentable* rather than merely rejected, because an index
outside `0..n-1` cannot name a title at all.

**4. Validation coerces before it compares, and counts its two drop reasons
separately.** See *Ground truth*: against a provider without guided decoding,
**108 of 108** identifiers came back as JSON integers where the schema asked
for strings. A validator holding a `set[str]` drops every row, writes no
curated rows, logs nothing, and is indistinguishable from a model that had
nothing to say. The hallucination rate in that same run was **zero**. So
`usher.curation.dropped` carries a `reason` label with two values —
`not_in_pool` and `unparseable` — and a run that drops everything for one
reason is visible as such.

**5. The candidate pool degrades without an embedder, and the taste centroid
is an additional signal rather than the pool's spine.** PRD 06 says the pool
is *"pre-filtered by taste-centroid proximity and popularity"*.
`USHER_EMBEDDING_ENABLED` defaults to `False`, so on the shipped deployment
there is no centroid at all — and implementing that sentence literally makes
curation the feature that never fires on the default configuration, which is
**exactly the failure PRD 06 already corrected once** for
`GenreAffinityProvider` (*"it fails in the direction hardest to notice"*). The
pool is therefore built from signals that need no model — unwatched, owned or
popular, genre affinity, `titles.vote_count` — and centroid proximity
**re-ranks** it when a centroid exists. This is also what finally gives
`TasteService.centroid` a caller in `src/`, which M7 shipped without and named
as a gap.

**6. `llm_calls` ships with a writer for every column, and PRD 02 gets the row
it never had.** [PRD 10](../prd/10-telemetry-and-dashboards.md) specifies the
table in a ten-column SQL comment and PRD 02's supporting-tables list does not
mention it. Both are fixed here. The `search_queries` discipline cuts *for*
this table rather than against it — M8 owns the writer and the table together
— but it binds every column: a column M8 cannot fill does not ship. **There is
no `user_id` on `llm_calls`**, deliberately and as specified: it is a cost
ledger, and PRD 10's Dashboard 5 joins spend to rows through `curated_rows`.

**7. No `usher.llm.*` metric is added, because PRD 10 says spend is SQL.**
*"Most of what is worth knowing about a media catalog is not a metric …
**LLM spend** … the catalog *is* the record."* Two metrics **are** added and
neither is about money: `usher.curation.rows` and `usher.curation.dropped`,
which are about whether the validator is eating the output — a question no
`llm_calls` row can answer, because a call that returned 200 and produced
nothing usable is `ok = true`. Spans: `curation.generate` under the worker's
`job.curate` root-with-a-Link, exactly as PRD 10 specifies for a job.

**8. Nothing schedules the nightly run, and this plan says so rather than
inventing a scheduler.** PRD 06 says generation *"runs nightly and on
demand"*. There is no scheduler anywhere in `src/` — `api/lanes.py` is one
lane per source plus one worker — and every other periodic thing in this
project is an operator's cron entry (`usher similar --rebuild`, `usher index
--backfill`), which PRD 10 already calls out as *"nothing schedules the
rebuild"*. `usher curate` is the command and the README carries the cron line.
Building a scheduler for one job would be a second unplanned milestone inside
this one, and the mechanism-before-the-setting rule
([PRD 08](../prd/08-operations.md)) forbids the alternative of a
`USHER_CURATION_SCHEDULE` with nothing reading it.

## Ground truth measured for this plan

Every number below was measured on this host between 2026-08-05 and
2026-08-06 UTC. The model measurements ran against a **local vLLM already
running on this host** serving `gemma-4-26b-a4b`
(`cyankiwi/gemma-4-26B-A4B-it-AWQ-4bit`, `max_model_len` 16,384) over
`http://127.0.0.1:8000/v1`. **Bounded deliberately at 45 completions total**,
from throwaway scripts outside the working tree, against a service that
belongs to something else on this machine — the same discipline the M6 GPU
probe applied when it declined to disturb a running container.

⚠️ **One model, one pool, one evening. Every rate below is scoped to that**
and none of them is a property of "an LLM". A hosted frontier model will do
better and a 3B model will do much worse; what transfers is the *ordering* of
the options and the failure *shapes*, not the percentages.

### The dependency, priced three ways

Marginal cost measured over a venv already holding Usher's own runtime
dependencies (106 MB, 114 site-packages entries), Python 3.13:

| option | venv after | marginal | distributions added | `import` (cumulative) |
|---|---|---|---|---|
| **`litellm` 1.95.0** | 252 MB | **+146 MB** | **29** | **1,343 ms** |
| `openai` SDK | 118 MB | +12 MB | 5 | 380 ms |
| **plain `httpx` — ships** | 106 MB | **+0 MB** | **0** | 41 ms |

**What the 29 distributions are is the argument, not the megabytes.**
`aiohttp` plus its five accessories (`aiohappyeyeballs`, `aiosignal`,
`frozenlist`, `multidict`, `propcache`, `yarl`) — a **second async HTTP
stack** in a process that already has httpx; `huggingface-hub`, `hf-xet`,
`filelock`, `fsspec`, `tokenizers` and `tiktoken` — a **model-download client
and two tokenizer runtimes**, which is the precise shape of unconditional
runtime that
[ADR-0022](../prd/decisions/0022-the-embedder-is-optional-and-its-contract-is-measured.md)
spent a whole decision refusing for the embedder; and the `openai` SDK itself,
which is an httpx client.

The 1,343 ms is the one that would be felt: imported at module scope it is
1.3 s on `usher --help`, against httpx's 41 ms. Lazy-importing it is possible
and is what `websockets` and `fastembed` do — but those are imported for a
capability, and this one would be imported to make a POST.

⚠️ **`litellm.__version__` does not exist.** The module's `__getattr__` raises
`AttributeError` for it, so anything wanting the version must use
`importlib.metadata.version("litellm")`. Recorded because the obvious probe
looks like the package is broken.

### Structured output against an OpenAI-compatible endpoint

`response_format: {"type": "json_schema", "json_schema": {"name": …,
"schema": …, "strict": true}}` is honoured, returns schema-conformant JSON,
and costs **314 ms** on a trivial call. `usage` carries `prompt_tokens`,
`completion_tokens` and `total_tokens`.

🔴 **`usage` carries no cost field, so `LLMUsage.cost_usd` cannot come from
the API** — which means PRD 10's *"litellm reports per-call cost natively, so
cost analysis is exact SQL rather than estimated counters"* is wrong about the
mechanism regardless of which client ships. litellm computes cost from a
bundled price table, which is a lookup this project would be shipping and
ageing. So `cost_usd` is `0` for a local model (**the honest value** — a local
completion costs no dollars) and comes from two configured per-million-token
prices otherwise, recorded on the row so a later price change cannot rewrite
history. PRD 10's sentence is corrected.

### How the prompt should name a candidate — three arms, one real pool

Pool: 200 real feature films sampled from the on-disk IMDb dumps
(`numVotes >= 50,000`, `titleType = movie`, `random.Random(20260806)`), three
further films as the household's recent history. Five completions per arm,
`temperature = 0.8`, seeds 2000–2004, identical prompt but for the handle
column, `json_schema` enforced on all three.

| handle | out-of-pool ids | prompt tokens | output tokens | median latency |
|---|---|---|---|---|
| **integer index `1…200`** | **0 / 105 — 0.0%** | **2,924** | **316** | **1,995 ms** |
| IMDb `tt` id | 2 / 107 — 1.9% | 4,050 | 440 | 2,794 ms |
| UUID | 3 / 105 — 2.9% | 9,041 | 957 | 6,474 ms |

The UUID arm is worse on **every** axis at once: 3.1× the prompt tokens, 3.0×
the output tokens, 3.2× the latency, and the highest error rate. A 200-title
pool addressed by UUID is 9k tokens before the history and the instructions,
which on a 16k-context model is most of the budget spent on identifiers.

**And 0.0% is not a guarantee.** It is 105 identifiers from one model. The
index scheme's real property is not its measured rate — it is that an index is
**bounds-checked**: `pool[i]` for `i` outside `0..n-1` cannot name a title,
where a hallucinated UUID is a well-formed identifier that merely denotes
nothing, and a hallucinated `tt` id may denote a *real film the household does
not own*.

### The pool that cannot answer the question

The pressure case, because the happy path cannot show it: the same 200-film
pool, and a prompt insisting on four rows about Studio Ghibli, Kurosawa and
the French New Wave — none of which the pool contains.

- **With `json_schema`: 0 out-of-pool over 81 ids.** The model narrowed rather
  than invented — it returned its four rows with *fewer* ids each (81 over 20
  rows, against 105 over 15 on the satisfiable prompt) and populated them from
  what was there. Worth knowing: the failure this milestone most fears did not
  reproduce on this model, under guided decoding, at this pool size.
- **With `json_object` (no schema): 5/5 parsed, 0 hallucinated — and a naive
  validator drops 100% of it.** See below.
- **With no `response_format` at all: 5/5 unparseable.** Every response was
  wrapped in a ` ```json ` fence. A client doing `json.loads(content)` fails
  every time.

### 🔴 The finding that changes the design: a type mismatch is indistinguishable from silence

The first run of the `json_object` arm scored **113 of 113 identifiers
out-of-pool** and read like catastrophic hallucination. It was not. Re-run
with the comparison instrumented over 108 ids:

| comparison | out-of-pool |
|---|---|
| strict — `id in set[str]`, the obvious spelling | **108 / 108 = 100.0%** |
| after coercion — `str(id).strip() in set[str]` | **0 / 108 = 0.0%** |

`json types seen = {'int': 108}`. Without guided decoding the model emitted
**the correct identifiers with the wrong JSON type**, on every single one. The
schema asked for strings; it returned numbers.

**What that produces in production:** a generation that ran, called the model,
got a good answer, wrote `llm_calls(ok = true)` with real token counts and a
real cost, dropped every row in validation, and left the household with no
curated rows — which is byte-for-byte the state of a household whose model had
nothing to say. No exception, no log line, no failed job, and PRD 08's
degradation table reads *"previous curated rows persist"*, so even the screen
looks deliberate.

Three consequences, all binding:

1. The validator coerces (`str(...).strip()`) before comparing, and the case
   that proves it feeds it integers.
2. `usher.curation.dropped` carries `reason` ∈ {`not_in_pool`, `unparseable`},
   so a total drop is legible as a *cause*.
3. A generation that validates to **zero** rows is a **failure**, recorded as
   `ok = false` with a reason, not a success that wrote nothing. This is the
   only place in the milestone where "the call succeeded" and "the job
   succeeded" are allowed to disagree.

## Traps

Ordered by how expensive they are to find late.

1. **`RowFamily.CURATED` changes the reachable screen length.** With two
   families the composer's longest screen is nine rows (1 pinned + 4 + 4);
   with three it is `_MAX_ROWS = 10`, and `_MAX_ROWS` becomes reachable for
   the first time. `services/home.py`'s own comment says so. Any case
   asserting screen length is now asserting something different.
2. **Three test files hard-code the registry in two different vocabularies.**
   `test_rows_invariants.py` asserts the nine **class names**;
   `test_services_home.py` asserts the nine **`slug_prefix`** values;
   `test_domain_rows.py` asserts `RowFamily` has exactly two members. All
   three must move in the same commits that make them false — each was written
   deliberately to fail here, and updating them silently is the failure they
   exist to prevent.
3. **`test_every_row_context_field_is_read_by_at_least_one_provider`
   AST-scans `services/rows/*.py`.** A `curated:` field added to `RowContext`
   for `CuratedProvider` must be read from a provider module or the case
   fails. The `taste` field was deleted for exactly this reason.
4. **`test_no_provider_reaches_a_port_the_context_does_not_carry`** forbids a
   provider module importing anything under `usher.db`, `usher.adapters`,
   `sqlalchemy`, or any `usher.*` outside `domain`/`ports`/`services.rows`.
   `CuratedProvider` reads its rows through a **port on the context**, never a
   repository it constructs.
5. **`test_every_provider_returns_nothing_against_an_empty_database` is
   parametrised over `ROW_PROVIDERS`** and runs at `2026-10-13` so
   `SeasonalProvider` gets a real chance to fire. `CuratedProvider` inherits it
   the day it is registered, along with four others — including *"does not
   fall back to popular titles"*, whose `may_fire` allowlist is a decision, not
   a formality. A curated row **is** a claim about the person, so
   `CuratedProvider` does **not** join that allowlist.
6. **The revision-id convention is exhausted.** M7's last three were `ffa`,
   `ffb`, `ffc` because the hex first character ran out at `f`. M8 opens a new
   convention: **`m08a`, `m08b`, …** — milestone-prefixed, obviously ordered,
   and unbounded. Recorded in `CLAUDE.md` in the same commit as the first one.
7. **`tests/integration/test_migrations.py`'s down/up cycle needs attention
   from every group that adds a migration**, and its `-1`-from-head half
   self-maintains into failing on the *previous* head's artefact. This bit M7
   twice. Re-point it in the same task that adds the migration, never later.
8. **`LLMPurpose` is a closed vocabulary and `test_ports.py` pins it.**
   `QUERY_EXPANSION` already exists as a member **nothing emits** — which this
   project forbids. That is the strongest single argument for building query
   expansion in M8 rather than deferring it again: the alternative is deleting
   the member.
9. **`tests/unit/test_no_third_party_data.py` scans `src/` and `tests/` for
   real third-party identifiers**, including a repo-wide scan for dataset
   *rows*. A prompt fixture holding a real TMDb id, a real IMDb id, or a
   pasted catalog row fails it. Prompt fixtures use the reserved synthetic
   bands.
10. **A secret reaches a third party here for the first time.**
    `USHER_LLM_API_KEY` is `SecretStr`; it goes in an `Authorization` header
    and never in a URL (the TMDb lesson —
    `HTTPXClientInstrumentor` records the full URL as a span attribute); and no
    exception message in `adapters/llm/` may carry a URL or a request body,
    for the reason `TmdbClient`'s module docstring already gives.
11. **The prompt is the request body, and a rejected request never echoes the
    body it rejected** (PRD 08). A `PortDataMalformed` from the LLM adapter
    must not interpolate the completion, which contains the household's watch
    history.
12. **`json.loads` on a fenced response fails 5/5.** The adapter strips a
    leading ` ```json ` / trailing ` ``` ` fence before parsing — measured, not
    defensive — and a case feeds it a fenced payload.
13. **A 4xx that is not 429 is `PortDataMalformed`, not `PortUnavailable`.**
    M4 learned this against TMDb and the same split applies: a 400 for a bad
    schema, a 401 for a bad key and a 404 for an unknown model are all
    permanent, and five retries reach the identical answer. 429 and 5xx are
    outages. A context-length 400 is the interesting one — it is permanent for
    *that* prompt and the fix is a smaller pool, so it parks with a message
    naming the token count.
14. **`Decimal` is not JSON-serialisable and is not a float.**
    `LLMUsage.cost_usd` is `Decimal` by construction (pinned by
    `test_llm_usage_cost_is_decimal_not_float`); the column is `NUMERIC`; and
    nothing may round-trip it through `float`.
15. **The genome tag vocabulary must match the vectors' `genome_revision`.**
    Loading `genome-tags.csv` from a different archive than the one that
    produced `genome_scores` silently mislabels 1,128 dimensions — every tag
    name off by however far the vocabulary moved. The loader writes the
    revision and the reader refuses a mismatch.
16. **A `curated_rows` row is per-user and the cache key already carries the
    user.** `RowCache` keys on `(user_id, slug)`. A curated slug that omitted
    the user would serve one household's LLM rows to another the day
    authentication lands — the failure `services/rows/cache.py` already
    documents for the screen key.

## What the contract cases must rule out

Each of these names an implementation that passes everything else.

**`LLMClient` (contract suite, run against the fake and — marked — against a
live endpoint):**

- Returns the parsed object *and* usage; an implementation returning only the
  object passes any test that asserts on content.
- A fenced response parses. (Kills `json.loads(content)`.)
- A 429 is `PortUnavailable`; a 400 is `PortDataMalformed`. (Kills one
  `except httpx.HTTPStatusError` arm.)
- `aclose()` is idempotent and closes the pool.
- The key is never in an exception message, a log line, or a URL.

**The validator:**

- An integer id for a string handle is **accepted**. (Kills the strict `in`.)
- An index outside the pool is dropped and counted `not_in_pool`.
- A row that ends up below the minimum length is discarded whole, never
  padded.
- A duplicate id inside one row collapses; the row is not thereby short.
- Zero surviving rows is a **failure**, not an empty success.
- The drop reasons are counted separately. (Kills one counter.) **Shipped as
  five rather than two** — see the amendment from Group D.

**The candidate pool:**

- It excludes what the household has watched — including via episode roll-up,
  the trap that returns films-only for a television household.
- It is non-empty on a household with no watch history at all (a cold start is
  the *normal* state), and it is not simply "the most popular 200 titles" on a
  household that *has* history. Both directions, because each alone is
  satisfied by a wrong implementation.
- With no embedder it still returns a pool. (Kills the literal reading of
  PRD 06.)
- With an embedder the ordering **changes**. (Kills a centroid that is read and
  discarded — the `RowContext.taste` failure exactly.)

**`CuratedProvider`:**

- Proposes nothing when the table is empty, and nothing when its rows are for
  another user.
- Hydrates stored output and **never** calls an `LLMClient`. Asserted
  structurally on the module's imports, the way
  `test_the_home_route_holds_no_source_adapter` is — "it did not raise" is
  also what a provider that swallowed everything produces.
- Its cards preserve the model's chosen **order**. A curated row is an
  ordering; re-sorting it by anything discards the only judgement being bought.

## Standing rules for every dispatch

Unchanged from M7 and restated because they are the ones that get dropped:

1. **TDD.** The failing test is written and *seen to fail* first, and the
   failure message names the wrong implementation.
2. **The PRD moves in the same commit as the change that invalidates it.**
3. **Every ordering case asserts its own premise** (`assert far_id < near_id`)
   — UUIDv7 makes `ORDER BY id` and `ORDER BY <the real key>` agree by
   accident, which cost M7 five untested orderings.
4. **A membership assertion is not an ordering test**, and
   `assert len(x) > 0` is not a relevance test.
5. **Every new port gets a contract suite run against both the fake and
   Postgres.** `TitleNeighborRepository` is the one port that skipped this and
   it hid a live defect.
6. **A fake's docstring enumerates every place it is more forgiving than the
   real thing.**
7. **Live verification runs from a throwaway script outside the working tree**
   and writes no credential, token, user id or host into the repo.
8. **`uv` for everything.** The gate is `uv run ruff check .`,
   `uv run ruff format --check .`, `uv run mypy src tests`,
   `uv run lint-imports`, `uv run pytest`.
9. **Commit trailers must be empty** — `git log -1 --pretty='%(trailers)'`
   prints nothing.

### From Group C (tasks 7–10)

1. **The migration-id convention is zero-padded: `m08a`, `m08b`, …** — commit
   `8794649`, from Task 8. It shipped one commit earlier as `m8a`, which is not
   ordered: `sorted(["m8a", "m9a", "m10a"])` puts `m10a` **first**, because
   `"1" < "8"` and string comparison never reaches the `0`. That is the exact
   failure the convention was introduced to avoid, arriving one milestone after
   it. Corrected in place in Task 8's body, in Task 19's (`m08b`), in the file
   map and in the group table. The full argument is the module docstring of
   `src/usher/db/migrations/versions/m08a_curation.py`, and the finding is in
   `.claude/rules/db-and-sql.md`.

2. **`CuratedRowRepository.replace_for_user` takes `(user_id, rows)` — there is
   no `generation_id` parameter** — commit `a85b896`, from Task 9. Task 9's
   body named a three-argument signature. The two sibling replace-ports pass a
   separate scope argument because the scope genuinely cannot be recovered from
   the rows (`seed_ids`, `title_ids` — a seed or title contributing *no* rows
   is the case they exist for); `TitleNeighborRepository.replace`'s
   `blend_fingerprint` is a parameter for the same kind of reason, because
   `ScoredNeighbor` has no such field. Neither transfers: the scope here is
   `user_id`, already a parameter, and `generation_id` is a **required field**
   of every `CuratedRow`. A third argument could only restate the rows, and a
   signature that can be handed one disagreeing with them eventually will be.
   What it would have caught is refused from the rows instead —
   `replace_for_user` raises `ValueError`, before writing anything, for a row
   belonging to another household or for a batch carrying two generations.
   **Tasks 11–13 call the two-argument form.** The full argument is on the port
   (`usher.ports.repository.CuratedRowRepository.replace_for_user`), including
   why `ValueError` and not a `UsherPortError`.

3. **`PostgresLLMCallRepository` lives in its own module,
   `src/usher/db/repositories/llm_call.py`, not in `curation.py`** — from
   Task 10. The file map above said `curation.py` held both; Task 9's module
   docstring had already refused that in the commit before, and the refusal is
   right: the two tables share a migration because one service writes both in
   one transaction, and they share nothing else — no column, no foreign key,
   no lifetime — so a module holding both would be one class that replaces and
   one that only ever inserts, sharing an import list. The **port** is in
   `ports/repository.py` beside `CuratedRowRepository`, as planned. File map
   corrected in place.

4. **`LLMCallRepository` has exactly one method, `record(call: LLMCall)`, and
   no read at all** — from Task 10. Three decisions worth carrying into
   Tasks 11–13 and 20:

   - **No read method**, because `m08a` shipped `llm_calls` with its primary
     key and no other index *on the strength of that*, and every reader PRD 10
     names is a Grafana panel M10 builds. A read here would be
     `ix_titles_popularity` (an index nothing read) and
     `PushHealth.record_reconnect` (a method nothing called) a third time. The
     read and its index arrive together, in the milestone with the panel.
     `test_the_cost_ledger_has_no_read_method` is what fails if that is
     reversed by accident; the contract suite observes writes through an
     abstract `LLMCallLedger` instead.
   - **It takes the domain model, not eleven parts.** A parts signature would
     rebuild the same `LLMCall` inside the repository and raise the same
     `ValidationError` one frame deeper — on the failure path, from inside an
     `except` handler, losing exactly the row the ledger exists for. **The
     caller's obligation is therefore explicit and Tasks 11–13 own it:**
     `error=str(exc) or type(exc).__name__`, never a bare `str(exc)`, which is
     `""` for an exception raised with no arguments and is refused by both
     `LLMCall._ok_and_error_must_agree` and `ck_llm_calls_ok_error_agree`.
   - **One call, never a batch, and `record()` returns nothing.** Curation
     makes one completion per generation and query expansion (Task 20) one per
     search — one per *request*, never a set flushed later, which the failure
     path could not tolerate anyway.

   The full argument is on the port
   (`usher.ports.repository.LLMCallRepository.record`), including why
   `RepositoryConflict` translation is load-bearing here even though the
   primary key is nearly unreachable: `cost_usd` is `NUMERIC(12, 8)` and
   `$36,000` on one call — a price scaled **up** by a million on the way in —
   is reachable from a *validly constructed* `LLMCall`.
   `src/usher/db/models/curation.py`'s module docstring holds the one copy of
   that mechanism; it shipped inverted in five places and every copy now
   points there.

### From Group D (task 13, dispatched ahead of 12)

5. **`usher.curation.dropped`'s `reason` label is five values, not two** — from
   Task 13. ADR-0028 said *"exactly two"* and is amended in place with the
   argument. `not_in_pool` and `unparseable` remain the load-bearing pair and
   the only one the 108/108 run is evidence for; `duplicate`, `row_unusable`
   and `row_too_short` join them because each names a different next step for
   an operator, and folding any of them into the original two reports a fix
   that is not the fix. Two of the five count **rows** and three count
   **cards**, which the `row_` prefix says out loud — summing the whole label
   set is meaningless. The tally always carries all five keys, zeros included,
   because a reason absent from a tally is indistinguishable from a reason
   nobody counts. Full argument in
   `src/usher/services/curation_validate.py`'s module docstring.

6. **The validator's return type is a union, so zero rows is unrepresentable as
   a success** — from Task 13. `CurationKept` refuses to be built with an empty
   `rows`, and `CurationRejected` has **no `rows` attribute at all**, so
   `for row in outcome.rows` on the failure branch is a `mypy` error before it
   is an `AttributeError`. A single dataclass with a possibly-empty `rows` and
   an `ok` flag would have made rule 3 a convention a caller can forget, which
   is the exact shape of the defect the rule exists for. **Task 12 matches on
   the two arms**; `CurationRejected.error` is what goes in `llm_calls.error`,
   and it is already checked against `LLMCall._ok_and_error_must_agree`.

7. **The pool reaches the validator as a `Mapping[int, UUID]`, and the
   validator does no arithmetic on it** — from Task 13. Which handles were sent
   is a fact the caller owns; a `Sequence` would have made the validator guess
   between `pool[i]` and `pool[i - 1]` (ADR-0028's measured prompt is
   **1-based**), and `pool[-1]` is legal Python that answers a hallucinated
   handle with a real film. **Task 12 builds that map** from
   `CandidatePoolService.for_user`'s list and renders the same integers into
   the prompt; `ROWS_KEY` / `TITLE_KEY` / `REASON_KEY` / `ITEM_IDS_KEY` are
   exported from the validator so the schema and the reader cannot drift.

8. **Two things Task 13 deliberately did not build, both of which Task 12 or 15
   inherits.** It does **not** cap the number of rows — every card in a
   hundredth row is still a title the household could watch, so a cap is a
   product bound and belongs with `CuratedProvider`'s `0–5 rows`; and it does
   **not** sanitise prose, because nothing downstream interprets a heading. The
   defence there is a *bound* (`MAX_TITLE_CHARS = 200`,
   `MAX_REASON_CHARS = 1000`, both chosen rather than measured) and a row past
   it is discarded whole rather than truncated. What it *did* take on beyond
   its brief is `curated_rows.slug`: minted here, and **zero-padded to the
   width of the generation**, which closes the `curated-1 < curated-10 <
   curated-2` tie-break defect `.claude/rules/db-and-sql.md` had filed for
   Task 15.

### From Group D (task 12)

9. **`CurationService` is not wired into `composition.Pipeline`, and Tasks 16
   and 18 own that wiring** — from Task 12. The service ships with its own
   file, its own cases and no caller, exactly as the validator did one task
   earlier. Two facts the wiring has to carry:

   - **`client: LLMClient` is required, never `LLMClient | None`.** A

     a `mypy` fact at the one layer that can know it, instead of an

   - **`model` is a required constructor argument** and is

     default is a second value that silently disagrees.

10. **`generate()` raises for two non-upstream conditions, and `usher curate`

      made; and
    - **a generation that validated to zero rows**, carrying
      `CurationRejected.error` — which is numbers and label names only, so it
      is safe to print.

    Everything else propagates unchanged, because a 429 carries a
    `retry_after` and a truncated completion is already malformed.

11. **The return type is `CurationReport`, and it carries what Task 18 prints**

    `curation_validate.py`'s `DEFAULT_MIN_CARDS` comment) and describe settings
