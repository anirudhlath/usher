## The one thing this milestone must not get wrong

**A wrong row renders identically to a right one.**

Everything M1–M6 built fails loudly or fails countably. An unreachable source
503s. A schema mismatch refuses to serve. A stale embedding is a predicate an
operator can `count(*)`. A search that returns the wrong thing at least returns
*something an operator typed a query for* and can judge in one glance.

A composed home screen has none of that. It returns ten rows of real titles,
hydrated, ordered, with plausible reasons attached, whatever it computes. A
`NextUpProvider` that returns a series' **first** episode instead of its **next**
one returns a valid, populated, correctly-shaped row — forever, silently, for
every series in the library. A `BecauseYouWatchedProvider` seeded from the
*oldest* watch state rather than the most recent returns a beautifully
constructed row about a film watched in 2019. A taste centroid computed over
the wrong sign returns the user's *least* favourite genre with total
confidence. None of those raise. None of those are empty. None of those are
distinguishable from working, by a human or by a test that asserts
`len(row.cards) > 0`.

So this milestone inherits M6's relevance rule and tightens it:

1. **Every provider case asserts on position, and seeds a distractor a broken
   implementation would rank first.** `assert title_id in {c.title_id for c in
   row.cards}` is satisfied by returning the whole library in physical order.
   M6 recorded this for retrieval; here it applies to nine providers at once,
   and here there is no query string to eyeball.
2. **A provider with nothing to say returns nothing, and the tempting fallback
   is the bug.** PRD 06: *"A provider returns nothing when it has nothing to
   say."* The failure mode is a provider that, finding no signal, falls back to
   "popular titles" — which produces a home screen that looks personalised and
   is not, on a household that has watched nothing. An empty row and an absent
   row are different states; a *generic* row is neither, and it is the one that
   survives review.
3. **Every provider names, in its docstring, the wrong implementation its
   cases rule out.** Same rule M6 put on `adapters/search/postgres.py`. A test
   whose docstring cannot name what it kills is a test that kills nothing.

The second-order version, which is what the composer must not get wrong: **the
composed screen is the only artefact here with no upstream to compare against.**
`title_neighbors` can be diffed against a fresh computation. `search_document`
has `test_the_stored_document_equals_a_freshly_computed_one`. A home screen has
no oracle, so the discipline has to live in the providers underneath it.

## Scope

M7 delivers the row hierarchy, nine of PRD 06's ten providers, the taste
centroid, the composed home screen and its route, the entities three earlier
milestones deferred to it (`Person`, `Credit`, `Collection`), the MovieLens tag

### The boundary calls

Nine of them, each with its reason, each also recorded in PRD 09 in the same
commit as the change it describes.

**1. `GET /home` IS built, and this is the first milestone since M5 to add a
client-facing route.** M6 declined routes and delivered through the CLI, and
three milestones before it did the same, so the default here is CLI-only. Four
things override it:

- **[ADR-0006](../prd/decisions/0006-server-composed-home.md) is the ADR that
  governs this milestone and its entire content is about the route.** *"The
  server composes. `/home` returns ordered, hydrated rows; clients render them
  in order."* Its central claim — *"One request paints a screen, which is what
  makes the home screen feel instant over a slow link"* — is a property of a
  request boundary and is not observable through a CLI at all. M6's boundary
  call 1 declined a route for capabilities the CLI genuinely delivers
  (`search`, `suggest`, `similar` each print exactly what the route would
  return). Composition is the first capability where the CLI is a *proxy* for
  the deliverable rather than the deliverable in another skin.
- **`row.invalidated` is assigned to M7 by name** (PRD 07's SSE table, and
  `ports/events.py`'s own docstring says the member is absent *"because nothing
  composes a row until M7"*). An invalidation event with no row to invalidate
  is an event with no consumer, which is the thing this project refuses.
- **M5's precedent covers the missing error envelope.** PRD 07's RFC 9457
  vocabulary is M9's, and M5 built `GET /titles/{id}` without it for a stated
  reason: *"M5 has no request whose honest answer is a domain-level failure."*
  `GET /home` has exactly that property — PRD 08's degradation table says
  *"LLM call fails → Home composes without them"*, and every other input is
  local state. There is no 503 here to give a `code` to.
- **`usher home` ships too**, because PRD 08's operator rule is that *"every
  one of them has to work against an empty database"*, and a route is a poor
  place to find out that composition divides by zero on a household that has
  watched nothing.

  **What is still M9's, so this call is a route and not a land grab:** the RFC
  9457 envelope, `usher.http.server.duration`, `usher.cache.hits`/`.misses`,
  HTTP cache headers, and pagination. `GET /home` returns the whole screen in
  one response with no cursor, which is what ADR-0006 specifies and what PRD
  07's own endpoint table shows (`/browse` carries a cursor; `/home` does not).

**2. `curated_rows`, `LLMRow` and `CuratedProvider` are not built. M8 owns the
family whole.** PRD 02 already says so (*"Does not exist yet — M8 owns it,
along with the `LLMClient` implementation that fills it"*), and PRD 06 says
`LLMRow.build()` *"only hydrates stored output"*. Hydrating a table whose
generator does not exist fixes that table's shape before anything has tried to
fill it — the `search_queries` failure PRD 10 argues at length, one milestone
early. `POST /admin/rows/regenerate` goes with it. Eight of PRD 06's ten
providers are built plus `RediscoverProvider`; `CuratedProvider` is the one
that is not, and PRD 06's table is annotated rather than silently shipped
short.

**3. `RowCard` carries no artwork field, exactly as `GET /titles/{id}` carries
no `images` key.** PRD 06 describes `RowCard` as carrying *"artwork refs"*, and
there is no `Image` table, no `images` column, and not even a `poster_path` on
`titles`. M9 owns the image proxy and the table. The choice is between an
always-null field and no field, and M5 already settled the identical question
one route over, in a sentence this call reuses verbatim: *"an empty list would
be indistinguishable from a film with no cast."* A `RowCard` with
`"artwork": null` on every card of every row is a client-side branch that never
takes its other arm, and the day M9 fills it, every client that shipped against
the null already renders without it.

**4. `Person` and `Credit` ARE built, and `Collection` with them, all three
re-derived from `raw_payloads` with no second network call.** This is M4's
boundary call 2 arriving at the milestone it named. Two providers depend on
them (`PeopleProvider`, `FranchiseProvider`), M6 reserved search weight class B
for exactly this, and `titles.collection_id` has been a bare nullable UUID with
no table since M1. The payload already holds all three: `credits.cast` and
`credits.crew` are in both `MOVIE_APPEND_TO_RESPONSE` and
`SERIES_APPEND_TO_RESPONSE`, and `belongs_to_collection` is a native top-level
field of `/movie/{id}`. Nothing is fetched.

**5. Weight class B is filled, and it needs a denormalised column on `titles`
because a generated column cannot reach another table.** M6 promised *"filling
B when M7 lands `Credit` is a migration rather than a rewrite"*, and that
promise is true only if class B is fed from a column of the row being
generated. `search_document` is `GENERATED ALWAYS AS (…) STORED`; a stored
generated expression may reference **only the current row** and must be
IMMUTABLE, so `setweight(to_tsvector('english', (SELECT … FROM credits …)),
'B')` is not expressible at all. So M7 adds `titles.credit_names text[]`,
maintained by the same derivation that writes `credits`, and class B is a
`setweight` over `usher_array_text(credit_names)`. That is still a migration
rather than a rewrite of the search path — but it is a *bigger* migration than
M6's sentence implies, and the correction goes into PRD 05 in the same commit.

**6. `title_search_names` is still not built, and M6's own condition for
building it is not met.** M6 deferred it to *"the day M7 lands aliases and
people"* — and M7 lands people but **not aliases**. `alternative_titles` is not
in either `append_to_response` list, so it is not in `raw_payloads` at all;
landing it means changing the crawl's request shape and re-fetching the whole
enriched tier, which is a metadata-provider change wearing a search table's
name. And the people half belongs with M9's two-tier suggest, which the failed
gate obliges and which replaces the shipped suggest path: building the narrow
table now means M9 redesigns against a table built for the design it is
replacing. **The condition is restated in PRD 05 rather than the deferral being
silently renewed**, which is the failure mode PRD 09 names for the tag genome
("an obligation recorded only where it was postponed is one nobody plans").

**7. The MovieLens tag genome IS built, and `genome_scores` is one dense
`halfvec(1128)` per title rather than PRD 02's implied tall table.** Measured
today on `pgvector/pgvector:pg17` (pgvector 0.8.6) at the real dimensions:
16,376 rows of `halfvec(1128)` is **45 MB**; the same data as
`(title_id, tag_id smallint, relevance real)` with a composite primary key is
18,472,128 rows and **2,106 MB** — **47×**, against a database PRD 08 budgets
at 8–12 GB *total*. `real[]` is 88 MB, in between and worse than both (no
operator class). The genome is a genuinely dense matrix — every one of the
16,376 movies carries a value for every one of the 1,128 tags, verified by
counting — so the tall form stores 16,376 copies of the tag id and the title id
to express a matrix that has no holes in it. And the dense form makes the
similarity term a single `<=>`, which is the operator `SimilarityService`
already blends. PRD 02's `genome_scores` row is corrected in the same commit.

**8. Rows build SEQUENTIALLY, and PRD 06's "builds the top N concurrently" is
corrected rather than implemented.** `AsyncSession` is explicitly not safe for
concurrent use — two coroutines awaiting on one session interleave on one
connection — so `asyncio.gather` over nine providers sharing the request's
session is not a performance choice, it is a corruption. The two ways out are
both worse than sequential at this scale: a session per row means nine
connections for one home screen, i.e. pool exhaustion at one concurrent user
against a default pool; and a semaphore has no lane to belong to (PRD 01's
concurrency table has no lane for this and PRD 08 already retracted
"concurrency per lane" as a setting, because *"a setting cannot be added ahead
of the mechanism it would bound"*). Every provider's query is a bounded local
read, `usher.home.compose.duration` is the measurement that says whether that
holds, and PRD 10's dashboard 4 wants exactly the per-provider breakdown that
makes revisiting this a number rather than an argument. **Task 34 measures it;
the plan does not assert it.**

**9. Row provider enable/disable does not become a table.** PRD 08 puts it in
the *database* layer — *"Sources, users, row provider enable/disable | Runtime,
via admin API"* — and the admin API is M9's. A table whose only writer is a
route in a later milestone is the `search_queries` failure again, and this one
would be worse: a `row_providers` table with nine rows all reading `enabled =
true` is indistinguishable from no table, right up until an operator finds it
and expects toggling it to do something. Providers are enabled by registration
in code in M7; PRD 08's row is annotated with its owner rather than left
implying a control that exists.

## Ground truth measured for this plan

Everything in this section was measured on 2026-08-03 on this host, for this
plan, and none of it was read from a summary. Where a PRD number disagrees, the
PRD is corrected in the task that touches it.

### The MovieLens dataset — and the newest release does not have a genome

`https://files.grouplens.org/datasets/movielens/` offers three archives that
carry a tag genome and one that used to be the obvious choice and does not.

| Archive | Released | Size (HEAD) | Genome? | Redistribution clause |
|---|---|---|---|---|
| `ml-32m.zip` | 05/2024 | 239 MB | **no** — four members only | *"The user may redistribute the data set, including transformations, so long as it is distributed under these same license conditions."* |
| `ml-latest.zip` | **20/07/2023** | **350,896,731 B** | **yes** | same permissive clause |
| `ml-25m.zip` | 03/12/2019 | 261,978,986 B | yes | *"The user may not redistribute the data without separate permission."* |
| `genome_2021.zip` | 12/2021 | 1,800 MB | yes, 9,734 movies | — |

**`ml-latest.zip` is the dataset, and the choice is forced rather than
preferred.** The newest full release dropped the genome entirely; the newest
release that *has* one and also carries the permissive redistribution clause is
`ml-latest`. `ml-25m` is the only genome-bearing archive whose licence forbids
redistribution — which changes nothing about what Usher ships (nothing), and
everything about what its licence row may claim.

`ml-latest`'s own README calls it *"a **development** dataset. As such, it may
change over time and is not an appropriate dataset for shared research
results."* That reads like M6's `CachedDatasetFile` trap arriving again — an
ETag-keyed cache in front of a moving file — and measured, **it has not moved
in three years**: `Last-Modified: Thu, 20 Jul 2023 20:20:32 GMT`, `ETag:
"14ea425b-600f0e149d407"`. IMDb regenerates daily and this does not, so the
same cache behaves completely differently in front of it. Recorded because the
*shape* of the hazard is identical and the conclusion is opposite.

`Accept-Ranges: bytes` on both archives, so `CachedDatasetFile`'s existing
resume path works unchanged.

### The genome itself, counted rather than quoted

Streamed and inflated in one pass, nothing stored:

- **18,472,128 rows**, **16,376 distinct `movieId`s**, **exactly 1,128.0 rows
  per movie** — the matrix really is dense, with no movie missing a tag.
- `relevance` ∈ **[0.00024999999999997247, 1.0]**, mean **0.1111**.
- `genome-tags.csv` holds **1,128 tags**, `tagId` 1…1128 contiguous.
- `links.csv` holds **86,537 movies**, `movieId,imdbId,tmdbId`, **zero empty
  `imdbId`, zero empty `tmdbId`**.

**PRD 04 is wrong in three places and each is corrected with the measurement:**
it says *"15.6M movie×tag relevance scores"* (18,472,128), *"250 MiB"*
(334.6 MiB — 250 MiB is `ml-25m`'s size, so the figure is right for the wrong
archive), and *"1,128-dimension relevance vectors for 13,816 movies"*
(16,376 movies; the 1,128 is exactly right).

**Coverage, with its denominator, because "~7%" has never had one.** PRD 05
promises *"~7% coverage"* and PRD 04 repeats it as *"~7% of the priority
tier"*. 16,376 genome movies against the catalog's 899,828 movies is **1.82%**;
against all 1,271,138 titles, **1.29%**; against PRD 04's own *"~189k titles
with ≥100 IMDb votes"* priority tier, **8.7%** — which is the denominator that
makes the published figure roughly right. **None of those is the number that
matters**, which is coverage of the *enriched tier* — an owned household
library of 2k–10k titles, skewed hard toward exactly the popular, English,
pre-2019 movies the genome covers. Task 36 measures it against a real catalog;
until then PRD 05's figure gets a denominator and a ⏳, not a new guess.

### `imdbId` in `links.csv` is zero-padded, and the join is `'tt' || imdbId`

Measured over all 86,537 rows: **79,978 are 7 characters wide, 6,559 are 8**,
none is shorter, none is empty. So `0114709` is Toy Story's `tt0114709` with
the prefix stripped and the padding kept, and an 8-digit id like `10147546`
needs no padding. `'tt' || imdbId` is therefore correct as written *and*
`'tt' || lpad(imdbId, 7, '0')` is correct too — the second is the one to write,
because the first silently depends on a padding convention the file documents
nowhere and a single unpadded row would join to nothing rather than raise. Same
family as M4's finding that 11 of 885 live Emby `Imdb` values were bare digits.

### `genome_scores` storage, three forms priced

On a scratch `pgvector/pgvector:pg17` (**pgvector 0.8.6**), 16,376 rows at the
real dimensions:

| Form | Rows | Total size |
|---|---|---|
| `halfvec(1128)`, one row per title | 16,376 | **45 MB** (1,096 kB heap + 43 MB TOAST + 624 kB index) |
| `real[]`, one row per title | 16,376 | 88 MB |
| `(title_id, tag_id smallint, relevance real)`, PK on the pair | **18,472,128** | **2,106 MB** |

A full pairwise cosine over every one of the 16,376 vectors — `Seq Scan`, no
index, because 16k rows never needs one — runs in **1.190 ms**.

**The vector is TOASTed and that is worth knowing before someone measures it
again.** 1,128 halfvec lanes is 2,256 bytes plus a header, past Postgres's
~2 kB inline threshold, so the heap holds 1,096 kB of pointers and the TOAST
relation holds 43 MB. Every read of a genome vector pays a TOAST fetch. At
16,376 rows and one `<=>` per candidate pair that is invisible; it would not be
at 1.27M rows, which is one more reason the population here is the genome's
own 16,376 and not the catalog.

### The gaps in the persistence layer, enumerated

Nine providers, and the layer answers none of their questions today. This table
is the shape of groups D and E.

| Provider | What is missing |
|---|---|

| Next Up | **no join from `watch_states` to `episodes` anywhere in `src/`**; no batch `get_for_episodes`; `EpisodeRepository.list_for_title` returns the entire tree (20,000 rows for the measured pathological series) |
| Recently Added | `media_items.added_at` exists and is **unindexed**; the only query using it is hard-filtered to `title_id IS NULL` (the review queue) |
| Because You Watched | `title_neighbors.list_for` exists; the *seed* list — recent high-engagement titles — does not |
| Franchise | `titles.collection_id` has no table, no FK, no index and no writer |
| Genre Affinity | `titles.genres` is `ARRAY(Text)` with no GIN index; no per-user aggregate of any kind exists in `src/` |
| Seasonal | `titles.release_date` and `episodes.air_date` both unindexed |
| People | no `Person`/`Credit` table; credits exist only inside `raw_payloads.payload` |
| Rediscover | needs "watched long ago and rated well"; `last_played_at` is unindexed and **`watch_states` has no rating column at all** |

**`watch_states` has no rating, and PRD 06's taste model assumes one.** *"The
taste centroid is the mean embedding of recently watched and **highly rated**
titles"*, and `RediscoverProvider` fires on *"Watched > 2 years ago, **rated
highly**"*. There is no `rating` column on `WatchState`, no `favorite`, and
`SourceWatchState` carries none either — Emby has both a user rating and
`IsFavorite` and the adapter reads neither. **M7 does not invent a rating
column**; it substitutes the engagement signal it actually has (`played`,
`play_count`, completion) and says so in PRD 06 rather than shipping a centroid
that quietly means something else. Landing a real rating is a source-port
change plus a contract case plus a live verification, i.e. an M9-shaped change
against a field no client can set yet.

## Traps

Six, each measured or read out of shipped code, each with the test that catches
it.

**Trap 1 — a generated column cannot see another table, so weight class B has
to be denormalised.** Covered in boundary call 5. The failure if it is missed
is not subtle (Postgres refuses the DDL), but the *design* failure is: a task
that discovers this halfway through writes a trigger instead, and a trigger
maintaining a tsvector is the staleness problem ADR-0020 exists to delete.

**Trap 2 — `compose_document`'s `credits` and `_FINGERPRINT_SQL` must move in
one commit, and `services/search.py:154-158` already says so.** The Python
composer builds the embedding text; the SQL fingerprint decides which titles
are stale. They are two spellings of one function and the suite has a
cross-check. Move only the Python side and every credited title matches the
stale predicate **forever**: the backfill re-embeds it, writes a fingerprint
the SQL cannot reproduce, and re-claims it on the next pass. An infinite
backfill that never errors. And note the *intended* consequence of moving both:
every fingerprint in the enriched tier changes at once, so the whole tier
re-embeds — which is ADR-0020's scheme working, not a bug, and is 25 s to 2 min
at the measured throughput.

**Trap 3 — `CREATE OR REPLACE FUNCTION` does not recompute stored generated
values, and adding a `setweight` term to `search_document` changes the
expression itself.** `fa2b6c1e9d30` carries the recipe (drop index, drop
column, replace function, re-add column, recreate index) and
`test_the_stored_document_equals_a_freshly_computed_one` is what catches a
migration that forgets. M7's class-B migration must force the full column
rewrite; a table half-computed under each definition has nothing to tell the
halves apart.

**Trap 4 — `AsyncSession` is not concurrency-safe.** Boundary call 8. The way
this ships wrong is that it *usually works*: two short reads interleaved on one
connection frequently complete, and the failure is an intermittent
`InvalidRequestError` or a result set attributed to the wrong query, under
load, in production. Do not write `asyncio.gather` over providers that share a
session, and pin the sequential build with a case rather than a comment.

**Trap 5 — a per-row watch-state event fans out per row per night.** PRD 07's
own note says the nightly walk deliberately publishes no `watchstate.updated`,
because *"a walk merges up to 1,126,789 states, and one … per merged row is a
fan-out per row per night to every connected client"*. `row.invalidated` and
taste-centroid invalidation are the same shape: PRD 06 says the centroid is
*"invalidated on watch-state change"*, and the walk changes up to a million of
them. Invalidation must be driven by the **push** lane and by demand reads, not
by the merge path, or M7 reintroduces the exact fan-out M5 refused.

**Trap 6 — `raw_payloads` has no `title_id` and no bulk read.** The join back is
`(provider='tmdb', kind=title.kind.value, reference=str(title.tmdb_id))`, and
`tmdb_id` is unique **per kind** (ADR-0011), so a derivation that keys on the
integer alone attaches a series' cast to a film. The port has `get`, `put` and
`oldest_fetched_at` and nothing that iterates, so the derivation needs a new
port method with a keyset cursor, its fake, and a contract case — not an ad-hoc
`SELECT` in a service, which contract three forbids anyway.

## What the contract cases must rule out

Every new port gets a contract suite run against both a fake and the real
implementation, per PRD 08. The table below is the *minimum* set of wrong
implementations each suite must kill — a reviewer implementing these
deliberately and finding the suite green is the M2 technique that has found a
real defect in every milestone since.

| Suite | A wrong implementation it must kill |
|---|---|
| `PersonRepository` | dedupes people by `name` rather than by `tmdb_id`, collapsing two directors who share a name |
| `CreditRepository` | drops `billing_order`, so "top billed" becomes provider-JSON order |
| `CreditRepository` | returns crew where cast was asked for, because `kind` is not filtered |
| `CollectionRepository` | writes `collection_id` onto a *series* from a movie's `belongs_to_collection` |
| `GenomeRepository` | returns a zero vector for a title with no genome row, instead of `None` (ADR-0014, fifth site) |
| `GenomeRepository` | stores the vector under `movieId` rather than the resolved `Title.id` |
| `WatchStateRepository.list_in_progress` | returns played titles, or ignores `position_seconds = 0` |
| `WatchStateRepository.list_in_progress` | orders by `id` (UUIDv7 insertion order) rather than by recency, which is *satisfied by a seeded fixture inserted in the right order* — the case must insert in the wrong order |
| `EpisodeRepository.next_up` | returns the series' first unplayed episode across all seasons rather than the one after the last played |
| `EpisodeRepository.next_up` | returns an episode from a season the user has not started |
| `TasteRepository` | returns a stale centroid after a newer watch state exists |
| `RawPayloadStore.iterate` | loses rows across a page boundary, or repeats them forever |

Unchanged from M6 except where noted. Repeated in full because every group is

- Layering is enforced: `domain/` imports nothing from `adapters/`, `db/`,
  `api/`; `services/` depends only on `domain/` and `ports/`. `uv run

- **Ship importers, never data.** Every new fixture is shape-recorded and
  value-synthetic. `tests/unit/test_no_third_party_data.py` scans four ways and
  M7 adds fixtures to three of the shapes it checks — IMDb ids must be in the

  kind on any commit.** Verify with `git log -1 --pretty='%(trailers)'` after
  every commit; it must print nothing.
